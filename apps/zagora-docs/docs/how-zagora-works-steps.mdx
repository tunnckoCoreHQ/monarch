A Zagora procedure is a plain function. A call runs up to seven steps, and each step has a design decision behind it. Reviews found the bugs that led to several of those decisions.

## The builder only collects a definition

Each builder method returns a new `Zagora` instance with one more field in its definition. Nothing runs until `.callable()`, or until `.handler()` in auto-callable mode. So a partly built chain is a plain value. You can share it, export it, and build many procedures on it.

The `.callable()` method reads the definition once and decides the async shape of the procedure. Two parts make every call async:

- An async handler. Zagora wraps the procedure, so every call returns a `Promise`. That includes a call whose input fails the schema.
- A schema with the `async: true` marker, such as a Valibot `pipeAsync` schema. Zagora wraps the procedure in the same way.

Other parts make a call async only when that call reaches them. Zagora adds no wrapper for them:

- A plain handler that returns a promise. A call that fails before the handler stays sync.
- An async cache adapter. Only a call that runs a cache method returns a `Promise`, so the return type is `Result | Promise<Result>`.
- A Zod schema with an async refinement. Zod has no async marker, so the type stays `Result` while the call returns a `Promise`.

The [async guide](/guide/async) has the full table.

## Step 1: Zagora validates the env values before the input

Zagora validates the env values first, before it looks at the arguments. A procedure with a wrong configuration then fails the same way on every call, whatever the input is.

The env values are not on the `~zagora` definition of the procedure. An early version kept them there, and a review flagged it in [#120](https://github.com/tunnckoCoreHQ/monarch/issues/120). Any code that got the function could read the secrets. The fix in [#121](https://github.com/tunnckoCoreHQ/monarch/pull/121) removed the values from the callable, and a test now checks that they stay out.

Before the merge, Zagora copies `process.env` with a spread. On Node, `process.env` is not a plain object, and the merge accepts only plain objects. The v1 review in [#176](https://github.com/tunnckoCoreHQ/monarch/pull/176) found that `.callable({ env: process.env })` threw for that reason.

## Step 2: the context

Zagora deep-merges the `.callable()` context over the initial context. Plain objects merge key by key. Any other value, such as a database client, replaces the initial value as it is, so the client keeps its prototype.

## Step 3: Zagora validates the input, and a tuple becomes real parameters

A tuple schema gives the procedure one parameter per element. Zagora detects the tuple through the schema structure of Zod and Valibot. A Zod transform wraps the tuple in a pipe, so Zagora reads the input schema of the pipe. After the validation, Zagora fills in the defaults of the missing trailing elements and spreads the values into the handler.

The types follow the runtime. Only the trailing elements that accept `undefined` become optional parameters. An early `SpreadTuple` type made required elements look optional, and [#121](https://github.com/tunnckoCoreHQ/monarch/pull/121) replaced it with one recursive type that works for a tuple of any length.

## Step 4: the cache key comes from the handler source

With a cache adapter, Zagora builds a key from the whole call: the validated arguments, the source text of the handler, and every schema. Unless `disableOptions` is on, the arguments include the options object, so the context and the env values are part of the key too. The key is a SHA-256 hash of that JSON.

The source text was a deliberate choice. [#121](https://github.com/tunnckoCoreHQ/monarch/pull/121) first used an in-memory ID for each handler, so that two handlers with the same source but different captured values could not share entries. [#123](https://github.com/tunnckoCoreHQ/monarch/pull/123) went back to the source text. An in-memory ID changes on every restart, so a shared external cache could not reuse any entry across processes. The [caching guide](/guide/caching) gives the rule that follows from this trade-off. Give each procedure that captures different values its own adapter.

A cache hit returns the stored value without a second validation. That is safe because of step 7. An entry can expire between the `has` call and the `get` call. Then the `get` returns `undefined`, and Zagora runs the handler instead of returning `undefined` as a success.

## Step 5: every thrown value becomes a result

Zagora calls the handler inside a try and catch wrapper. A sync handler that returns a value gives a sync result, because the Zagora source has no `async` and no `await`. Zagora waits only when a value is a promise, or a thenable such as a query builder.

A thrown value goes through the error map, with three outcomes:

- A declared `kind` with valid data becomes that typed error.
- A declared `kind` with invalid data becomes a `VALIDATION_ERROR`, and its `key` is the kind.
- Any other value becomes an `UNKNOWN_ERROR`, with the value in `cause`.

The wrapper also handles thrown values that break the usual shape, such as a symbol `kind`, or a `kind` or `stack` getter that throws. Each of those cases once made the call throw, and each now has a test.

## Step 6: the output schema sets the type of the data

With an output schema, Zagora validates the return value of the handler. A transform in the output schema changes the value that the caller gets, so `result.data` has the output type of the schema. Without an output schema, Zagora returns the value of the handler as it is.

## Step 7: only valid output reaches the cache

Zagora writes only output that passed step 6. An early version cached the raw handler result, so an invalid result stayed in the cache, and every later call returned it. [#121](https://github.com/tunnckoCoreHQ/monarch/pull/121) moved the write after the validation. That move is what lets step 4 skip the validation on a hit.

## Why one result shape

Every step can fail, and every failure becomes a frozen error object in the same result shape. A caller checks `result.ok`, and TypeScript narrows the rest. The design leaves out a `try` block, an error class, and an unwrap step. A test can assert on the result directly, and a router can map `error.kind` to a status code with one object. The [comparison](/comparison) page shows how this differs from neverthrow and Effect.
