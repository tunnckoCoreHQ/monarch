---
title: Validate input and output
description: Validate the arguments and the return value of a procedure with any Standard Schema library, and see how each schema shape maps to function arguments.
---

The input schema validates the arguments before the handler runs. The output schema validates the return value after the handler runs. Both can come from any [Standard Schema](https://standardschema.dev) library, and one procedure can mix libraries.

## Pick the input schema for your arguments

The shape of the input schema sets the signature of the procedure.

| Input schema                         | Procedure     | Handler, after the options object |
| ------------------------------------ | ------------- | --------------------------------- |
| none                                 | `()`          | nothing                           |
| primitive, such as `z.string()`      | `(value)`     | `value`                           |
| object, such as `z.object({...})`    | `(input)`     | `input`                           |
| array, such as `z.array(z.string())` | `(items)`     | `items`                           |
| tuple, such as `z.tuple([...])`      | `(a, b, ...)` | `a, b, ...`                       |

Only a tuple spreads into several arguments. An array stays one argument. The [tuple arguments](/guide/tuple-arguments) page explains the tuple case.

### Primitive input

```ts twoslash
import { z } from "zod";
import { zagora } from "zagora";
// ---cut---
const shout = zagora()
  .input(z.string())
  .handler((_, text) => text.toUpperCase())
  .callable();

shout("hello world");
// { ok: true, data: 'HELLO WORLD', error: undefined }
```

### Object input

```ts twoslash
import { z } from "zod";
import { zagora } from "zagora";
// ---cut---
const describe = zagora()
  .input(z.object({ name: z.string(), age: z.number().default(18) }))
  .handler((_, { name, age }) => `${name} is ${age}`)
  .callable();

describe({ name: "Ada" });
// { ok: true, data: 'Ada is 18', error: undefined }
```

### Array input

```ts twoslash
import { z } from "zod";
import { zagora } from "zagora";
// ---cut---
const upper = zagora()
  .input(z.array(z.string()))
  .handler((_, items) => items.map((item) => item.toUpperCase()))
  // items: string[]
  .callable();

upper(["foo", "bar"]);
// { ok: true, data: ['FOO', 'BAR'], error: undefined }
```

## The handler gets the output type of the schema

A schema has an input type and an output type. The two types differ when the schema has a default or a transform. The procedure accepts the input type, and the handler gets the output type.

```ts twoslash
import { z } from "zod";
import { zagora } from "zagora";
// ---cut---
const parsePort = zagora()
  .input(z.string().transform((value) => Number(value)))
  .handler((_, port) => port + 1)
  // port: number
  .callable();

parsePort("8080");
// { ok: true, data: 8081, error: undefined }
```

## Validate the return value

With an output schema, zagora validates the return value of the handler. An invalid return value becomes a `VALIDATION_ERROR`, and its message starts with `Output validation failed`.

```ts twoslash
import { z } from "zod";
import { zagora } from "zagora";
// ---cut---
const age = zagora()
  .input(z.number())
  .output(z.number().min(0))
  .handler((_, years) => years - 100)
  .callable();

age(30);
// {
//   ok: false,
//   isTypedError: false,
//   error: {
//     kind: 'VALIDATION_ERROR',
//     message: 'Output validation failed: (root) => Too small: expected number to be >=0',
//     ...
//   }
// }
```

The output schema also types `result.data`. A transform in the output schema runs on the return value, and `result.data` has the transformed type.

## Read a validation error

Every validation failure has the same shape.

```ts
{
  kind: "VALIDATION_ERROR";
  message: string; // "Input validation failed: name => expected string, received number"
  issues: readonly StandardSchemaV1.Issue[];
  key?: string; // set only when typed error data fails
}
```

The message starts with the part that failed, which is `Input`, `Output`, `Env`, or `Error data`. Then it lists each issue as `path => message`, with `; ` between issues. A path is the keys joined with dots, and `(root)` means the whole value. The `issues` array is the original list from your schema library.

## Use another schema library

Validation works the same way with Valibot, ArkType, and every other Standard Schema library. You can mix libraries in one procedure.

Tuple spreading is different. zagora spreads a tuple only when it recognizes the tuple schema, and it recognizes Zod and Valibot tuples.

```ts twoslash
import * as v from "valibot";
import { z } from "zod";
import { zagora } from "zagora";
// ---cut---
const add = zagora()
  .input(v.tuple([v.number(), v.optional(v.number(), 1)]))
  .output(z.number())
  .handler((_, a, b) => a + b)
  .callable();

add(2);
// { ok: true, data: 3, error: undefined }
```

## A schema that throws gives an UNKNOWN_ERROR

A schema can throw instead of returning issues, or an async schema can reject. zagora does not report a validation failure then. It returns an `UNKNOWN_ERROR` with the message `Unexpected failure during input validation`, and the thrown value is in `error.cause`. For the other schemas, the message has `output`, `env`, or `error data` in place of `input`.

An env schema that is async always fails with a different `UNKNOWN_ERROR`, because zagora does not support async env schemas. The handler does not run when the input schema fails.
